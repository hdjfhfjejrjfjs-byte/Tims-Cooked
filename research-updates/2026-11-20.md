## Later static checkpoint — 2026-11-20 (pager-ready producer census)

- Enumerated every kernel store of a word at the candidate virtual-memory-object flags offset that sits near an `#0x200` logical operation: 59 sites per build, zero atomic read-modify-write sites.
- Identified the two virtual-memory-object writers of the “pager ready” bit: the pager-association routine behind the freezer/pageout chain (sets the bit only when the object’s internal flag is set, with companion state changes) and a memory-object attribute handler whose callers are the vnode/device/shared-region/dyld/swapfile/apple-protect pager initialisers.
- Corrected the association-producer identity recorded in earlier local notes: it is the routine called from the freezer pageout wrapper, not the attribute handler.
- Classified four previously unclassified candidate stores as VFS/vnode, network-interface, packet-buffer and Skywalk host-networking state; matching offsets and bit numbers alone do not establish object identity.

## Later static checkpoint — 2026-11-20 (interned entitlement-key readers)

- Runtime checks of DriverKit/user-client entitlements do not re-read the key string: the kernel interns the standard IOKit property keys once into a global symbol table. A strict address-reference census of that table settles who reads each key.
- The `IOServiceDEXTEntitlements` key has exactly three reader functions, all inside the DriverKit/dext cluster (one of them the already-known user-client creation gate). This independently reproduces an earlier local result with exact addresses instead of an inference; no fourth reader exists in the kernel core.
- Named for the first time: the single kernel-core reader of the generic `IOUserClientEntitlements` key, an indirectly entered routine reached from one caller whose input validation looks message-shaped. Whether it enforces anything or only queries, and which subsystem owns its entry, are not established.
- Two published scanner false positives for these tables were reproduced and their cause recorded (a register-invalidation step that never fires in this toolchain), plus a corrected scanner.
- No candidate path is reopened by this, no device run was possible, and no vulnerability, kernel read/write primitive, or jailbreak is claimed.

## Later static checkpoint — 2026-11-20 (AppleJPEGDriver validator reference corrected)

- An earlier checkpoint recorded the AppleJPEGDriver request-processing routine as having no references and its validation chain as possibly never executed. Both statements were wrong: they came from running an address-reference scanner with a truncated (low-32-bit) address, which returns zero hits silently while the rest of the run looks clean.
- With the full 64-bit address, six genuine code references exist. All six are decoder/encoder entry bodies: each materialises the routine's address, signs it with pointer authentication, and passes it as the action argument to the driver's command-gate dispatch primitive together with the request pointer.
- The routine names itself as the driver's queued-I/O worker and calls the two request-validation routines that log a failed request validation or setup. Those checks therefore run — on the command-gate thread, after the external-method call returns — and the earlier bounded negative (no reachable input-structure access leaves its declared size) stands with live checks behind it.
- The dispatch-primitive identification rests on the driver's own field and string naming plus the argument shape and two independent controls elsewhere in the same driver; the callee body at that vtable slot was not itself disassembled, so the primitive's exact symbol is inference rather than proof.
- New open lead, untested: because processing is deferred, the request object must outlive the call that enqueued it. Whether any app-reachable close or abort ordering can drop the last reference first is unresolved; no use-after-free or dangling-pointer claim is made.
- No device run was possible this cycle (no authorised Mac enumerated a device). No vulnerability, kernel read/write primitive, or jailbreak is claimed.

## Later static checkpoint — 2026-11-20 (AppleJPEGDriver cross-build check)

- The open question from the previous checkpoint was whether the deferred-request lifetime boundary had been hardened upstream. A cross-build check answers it negatively for this driver: iOS 27.0.1 (build 24A446) and iOS 27.2 (build 24B119) contain the same number of functions in the AppleJPEGDriver kernel extension (1,807), and an index-paired comparison of every function's instruction stream finds zero differing functions — same mnemonics, same register operands, same memory-base operands, same sizes.
- This covers all six decoder/encoder entry bodies, the queued-I/O worker, the completion routine, the client-teardown routine and the request-validation chain. A separate alignment pass reported 167 "changed" blocks that a per-function shape re-check classified as pure address/data-segment drift (drift 167, real edits 0).
- Scope caveat: immediates and branch targets are masked in that comparison, so a fix that changed only a constant without altering any instruction shape would not appear. Nothing of that kind is indicated for this member; treat the result as "no instruction-level change", not "bit-identical".
- The four imported-helper targets used by the entry bodies were disassembled. One is a flag-selecting allocator-shaped wrapper over a descriptor-based allocation helper; another is a one-instruction thunk to a descriptor-shaped free/delete helper that derives a zone from the object address and verifies an element size before releasing; the other two are object-lifetime-shaped helpers that store a signed vtable, adjust refcounts and call virtual slots. These identities are inference from instruction shape, not symbol proof.
- New unresolved detail: the first argument passed to those helpers is a pointer into the extension's constant data that reads as zero in the file and is written by nothing in the extension; its runtime initialisation path is not established, so it must not be described as a class or zone.
- The retention question itself stays open: the queued-I/O worker does not store the request pointer into any driver field, so whether anything keeps the request alive between enqueue and gate execution is still unproven. No use-after-free, dangling-pointer, kernel read/write primitive or jailbreak is claimed.
- No device run was possible this cycle (no authorised Mac enumerated a device). No new app build is claimed.

## Correction — historical socket peer-delivery observations (2026-11-20)

- Source review found that the race increments `entered` immediately before `sendmsg`, then closes the target descriptor and allocates reclaimer sockets without an fd placeholder or numeric-fd check. `entered` therefore does not prove the kernel resolved the descriptor before close; ordinary fd reuse can explain the observed peer bytes and TCP→UDP datagrams.
- The historical 20 precision peer-delivery hits and 109/4 UDP events are observations, not UAF or socket-object-reclaim hit counts. The `sockfield` follow-up scanned API options on hammer descriptors without identifying which kernel object backed any fd, so its zero field-differential is not a validated negative on a reclaimed object.
- No device rerun was made. The CVE-2026-112514 attribution and the proposed fix mapping remain unverified for the target; no kernel read/write primitive or jailbreak is claimed. See the [detailed correction](2026-11-20-socket-fd-reuse-erratum.md). No new app build was made; the existing sanitized v0.6 IPA is unchanged.
